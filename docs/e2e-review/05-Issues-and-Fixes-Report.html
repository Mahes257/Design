Testing exposed five root-cause issues. Four affected cross-module integrity: new projects were missing from support lookups; approvals could bypass checklists; controlled release did not release the linked documents; and transfers could not see newly released baselines. One affected the sales conversion path: a ready enquiry had no direct quotation action. All five were repaired and retested through the workflows that exposed them.

Repair boundary. The objective was to fix integration gaps, not redesign the application. Existing shells, themes, reusable components, routes and seeded records were preserved. New behavior is limited to the workflows described below.

3. Root cause and repair detail

ISS-01 · Support project lookups

Root cause. The case form, support register and case detail resolved projects through the static PROJECTS fixture instead of the live ProjectsContext. A project created by quotation conversion existed in state but not in that fixture.

Repair. Support pages now use useProjects() for the project option list, register filter and detail label. Static support case types and field definitions remain unchanged.

Files. src/pages/support/CaseFormPage.jsx, src/pages/support/SupportModulePage.jsx, src/pages/support/CaseDetailPage.jsx.

ISS-02 · Enquiry-to-quotation conversion

Root cause. The quotation form already accepted a linked enquiry through ?enquiryId=, but the enquiry detail header exposed only Register, Edit and Update Status. The conversion was possible only by creating a quotation elsewhere and selecting the enquiry.

Repair. Added a status-aware header action:

  • Create Quotation when status is Ready for Quotation and no linked quotation exists; opens the quotation form with the enquiry ID.
  • Open Quotation when a quotation is already linked; opens the existing quotation instead of allowing a duplicate.

File. src/pages/customer-enquiries/CustomerEnquiryDetailPage.jsx.

ISS-03 · Approval checklist enforcement

Root cause. The engineering and manufacturing decision actions checked only the review stage, not checklist completeness. The engineering workspace rendered the technical checklist as a read-only summary, so a new review could be approved while every design and technical item remained Pending.

Repair.

  • The technical checklist is now editable with result, reviewer, comments and evidence fields.
  • Engineering approval is disabled while any design or technical item is not Pass or N/A; a banner reports the pending count.
  • Manufacturing approval is disabled while any manufacturing item is not Pass or N/A; a banner reports the pending count.
  • Reject and Request Changes remain available while items are pending, so a review can still be returned.

Files. src/pages/approvals/EngineeringReviewTab.jsx, src/pages/approvals/ManufacturingReviewTab.jsx.

Verification. REV-2026-001 opened with 6 pending design/technical items; Approve was disabled and the banner reported 6. Changing technical item TC-4 from Pending to Pass updated the chip to 4/6 and the banner to 5 pending; reverting restored 6. No review data was left changed by the test.

Historical test record. REV-2026-013 was approved before this gate was added and remains Approved with its original checklist state for traceability. It is test data, not a production record. The gate is verified on a seeded in-review record.

ISS-04 · Controlled release propagation

Root cause. releaseReview created a release object inside the approval review and wrote release history, but it did not call the CAD or BOM release actions. Release eligibility looked correct inside the approvals module while the linked drawing still showed Approved / Not released and the BOM remained Approved.

Repair.

  • releaseDrawing accepts an optional controlled release reference.
  • releaseBom accepts an optional controlled release reference.
  • Controlled release calls these actions for the exact linked BOM/drawing revisions when they are still Approved, then creates the approval release record.
  • If a linked document is already released, propagation is skipped rather than failing the release.

Files. src/context/ApprovalsContext.jsx, src/context/CadContext.jsx, src/context/BomContext.jsx.

Verification. After release, the drawing showed approval Released, release Released and reference REL-REV-2026-003; the BOM showed status Released and the same reference. Both records then appeared in the transfer source selector.

ISS-05 · Live transfer sources and project validation

Root cause. The transfer form imported a fixed SOURCE_DELIVERABLES array. Controlled release updated the live BOM and CAD state, but that state was never merged into the selector. Project validity used the static PROJECTS array, so PRJ-2026-042 was reported invalid and the project label fell back to “PRJ-2026-042 · PRJ-2026-042.”

Repair.

  • NewTransferPage now reads released BOMs from BomContext and released drawings from CadContext.
  • Live sources include the linked approval review, release reference, release date, BOM items, derived material requirements, attachments and destination eligibility.
  • A released drawing carries its linked released BOM items and materials into purchase validation.
  • Static fixtures remain as fallback, with duplicates by deliverable type, number and revision suppressed.
  • sourceFor has a snapshot fallback so a transfer created from a live source can still resolve its display context after reload.
  • Project existence and display names resolve against seeded and persisted projects; transfer validation uses the same resolver.

Files. src/pages/transfers/NewTransferPage.jsx, src/data/transfersData.js, plus the release propagation described in ISS-04.

Verification. E2E BOM Rev A validated with 12 valid, 1 warning and 0 invalid, and created TRF-2026-011. E2E drawing Rev A validated with 12 valid, 1 warning and 0 invalid, and created TRF-2026-012. The project label rendered correctly as PRJ-2026-042 · E2E Testing – Mechanical Product.

Cleanup options

  1. Full local reset (recommended for demo handover): use the application’s Reset Seed Data action. This restores the seeded workspace and removes all E2E records and local edits, including settings and theme changes. Export any data you need first.
  2. Selective cleanup: delete or archive E2E records from their registers and cancel the two E2E transfers that are still Ready for Transfer. Some linked records (review, release, support case) do not offer delete and require a full reset for complete removal.
  3. Browser storage cleanup: clearing site data for the localhost origin removes all md-*-state-v1 keys. This is destructive to all local records.
Do not use Reset Seed Data if the workspace contains real user-entered data that has not been exported. There is no server backup.

8. Closure

All five root-cause issues are fixed and retested. The final production build passes. The main E2E flow reaches a controlled release and creates validated purchase transfers from the newly released baseline. Remaining blocked items are intentional gates, and the remaining limitations are architectural or content-related rather than functional regressions.

Next recommended step: run a second regression cycle focused on production handover after implementing a released manufacturing package, then replace the seeded analytics and tracking data with live aggregation before operational use.
